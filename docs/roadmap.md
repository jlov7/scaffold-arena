# Roadmap

Scaffold Arena 0.9.1 is an undeployed beta release candidate. The current Workbench and its provider-free fixture paths are implemented, but the repository does not record a comparative live study, completed human calibration, independent reproduction, or a current deployment. [Evidence status](evidence-status.md) is authoritative.

## Implemented workbench boundary

The candidate includes versioned StudyPacks, frozen experiment designs, deterministic-first evaluation, durable executions and recovery, analysis, trace diagnostics, evidence custody, and a provider-free `offline-demo-v1` fixture. It also includes bounded X-Ray, observatory, counterfactual, Harness CI, and planning surfaces. These are protocol, product-control, fixture, or recorded-evidence capabilities within their documented limits; they are not evidence of a general scaffold advantage, security assurance, or deployment readiness.

## Evidence work before stronger research claims

The next evidence milestones are requirements, not delivery commitments:

1. Freeze and publicly identify a protocol, candidate revision, model or runtime identities, controls, analysis plan, custody rules, and exclusion policy before any live comparison.
2. Record live runs under that frozen protocol with enough provenance to distinguish fixture controls from provider or runtime behavior.
3. Complete blinded human calibration and preserve agreement, adjudication, and completion custody.
4. Obtain an independently attributable reproduction or substantive external critique.
5. Obtain an appropriate independent security assessment before making security or containment claims.

No local gate, fixture, historical-integrity binding, or deployment receipt can satisfy those milestones by itself.

## Historical deployment parity

An earlier deployment-parity check for merge `002fe74fbab99bb5adf611b857b05cfd17dc3f53` recorded matching public build identities and a token-free smoke result. It is historical revision-coherence evidence only. It does not establish deployment of the current candidate, deployment security, research validity, or independent assurance.

## Future publication path

Before public release, prepare an exact candidate, review its public tree and hosted surfaces, enable a verifiable private vulnerability-reporting route, and run the release gates for that exact candidate. A tag-gated workflow must publish and verify the resulting artifacts, signatures, attestations, and release record.

If a future public repository is created as a clean-history snapshot, retained historical local-runtime bundles require the separate root-commit publication binding described in [evidence status](evidence-status.md). That binding preserves bundle integrity and custody only; it does not reproduce historical source or create new evidence.
